# Cross-Subject Benchmarking

Run the same eval against N **subjects** — where a subject is anything you can
swap behind the agent's entry point: a model, a framework, a prompt variant,
a temperature, or a fine-tune — and compare them on the same rubric.

## When to use this

**Use cross-subject when** you're trying to answer a *comparative* question:

- "Does GPT-4o or Claude 4.5 do our task better?"
- "Is PydanticAI or LangGraph faster / more reliable on Bedrock Opus?"
- "Does the new system prompt actually improve the output, or am I imagining it?"
- "What does latency cost us per quality point?"

**Stay single-subject when** you're iterating on *one* agent's quality. Adding
a second subject triples the harness surface area — don't pay that cost
until the comparison is the actual question.

## The dispatch pattern

Every subject must return the same **7-field metadata contract**
(see `SKILL.md` → "Metadata contract"). Once they do, a single dict switches
between them:

```python
# evals/eval_harness.py
from src.agent_v1 import run as run_v1
from src.agent_v2 import run as run_v2

FRAMEWORKS: dict[str, Callable[[str], dict]] = {
    "raw_anthropic":        run_v1,   # baseline
    "raw_anthropic_terse":  run_v2,   # shorter system prompt
    # "langgraph":          run_lg,   # add more subjects here
}
```

Rename to `SUBJECTS` if that reads better for your case — the benchmarking
literature uses both. Keep the key usable as a filename (`pydantic_ai`, not
`PydanticAI 0.0.14`) — it becomes `reports/raw/<key>.jsonl`.

## The `--framework all` flag

Add one flag to your CLI that loops every subject over every test case:

```python
ap.add_argument(
    "--framework",
    default="raw_anthropic",
    choices=[*FRAMEWORKS.keys(), "all"],
)

# In main():
subjects = list(FRAMEWORKS.keys()) if args.framework == "all" else [args.framework]
for subject in subjects:
    run_agent = FRAMEWORKS[subject]
    raw_path = RAW_DIR / f"{subject}.jsonl"
    with raw_path.open("w") as raw_f:
        for case in test_cases:
            for trial in range(1, args.trials + 1):
                result = run_agent(case["input"])
                # ...judge, aggregate, write JSONL row...
```

One JSONL per subject. Same test cases, same order, same rubric. The raw
files are the single source of truth — the per-subject markdown and the HTML
dashboard are both rendered from them.

## Fairness: keep everything identical except the subject

The comparison is only meaningful if the *subject* is the only thing that
varies between runs.

1. **System prompt: byte-identical** across subjects, unless the subject
   *is* the prompt. Store it in `common/prompts.py` and import it from each
   adapter.
2. **Model + temperature**: hold constant unless the subject *is* the model.
   Pin `temperature=0` (or a fixed non-zero if you're measuring variance).
3. **Tool implementations**: the exact same Python functions, not
   framework-specific reimplementations. Share via `src/tools.py`.
4. **Test cases**: all subjects run the full seed set in the same order. Do
   not cherry-pick.
5. **Trials per case**: same `--trials N` across all subjects.
6. **Judge**: one judge model, one judge prompt, one rubric. The judge is a
   constant, not a variable.
7. **Seed / determinism**: if your agent has any randomness (sampling,
   retrieval), seed it so runs are reproducible.

A useful sanity check: run the *same* subject twice as
`"raw_anthropic"` and `"raw_anthropic_again"`. Their weighted scores should
be within ~0.02 of each other. If they're not, your eval has more noise than
you think — fix that before trusting a cross-subject delta.

## Watch for leniency-per-subject

The judge scores outputs, and different frameworks produce outputs with
different *styles* — verbose vs terse, JSON-only vs prose-wrapped,
Pydantic-clean vs dict-sloppy. That style can interact with the judge's
priors.

Symptom: one subject has dramatically higher leniency (|judge − human| per
dimension) than the others on the easy reference cases.

If you see this, flag it in the report. Don't silently trust a leaderboard
where one subject's judge scores are +0.4 lenient and everyone else is
+0.05 — you're measuring style agreement, not task quality.

Your leniency column in the leaderboard should show the per-subject number,
not an average. See `references/rubric-design.md` → "Leniency tracking" for
the calibration loop.

## Reporting

Two layers:

1. **Per-subject markdown** — one file per subject, already generated by the
   single-subject harness. Keep these; they're the per-run deep-dive.
2. **HTML dashboard** — `reports/framework-comparison.html` rendered from
   all `reports/raw/<subject>.jsonl` files. See
   [html-report-template.html](html-report-template.html) for the template
   and companion generator.

The dashboard has five panels: leaderboard table, per-dimension radar,
per-case heatmap, latency + token bars, and failure-category breakdown.
Sort the leaderboard by weighted_score descending. Expose the full per-case
scores on hover — the reader will want to drill in.

## Adding a new subject (5-step checklist)

1. **Write the adapter.** Implement `run(prompt: str) -> dict` returning the
   7-field contract. Crib from `references/framework-adapters.md` if the
   subject is a new framework.
2. **Share the system prompt and tools** with the other subjects — import
   them, don't retype them. If the subject *is* a prompt variant, keep the
   prompts side-by-side in one file so diffs are visible.
3. **Register it** in `FRAMEWORKS` with a filename-safe key. Add any extra
   dependencies to `pyproject.toml`.
4. **Smoke-test one case end-to-end**:
   `python eval_harness.py --framework <new> --test-case easy-01 -v`.
   Confirm recommendation parses, tool_calls > 0, tokens populated, judge
   scores come back.
5. **Run the full suite and re-render the dashboard**:
   `python eval_harness.py --framework all` → `python make_html_report.py`.
   Verify the new subject appears in the leaderboard, the radar, and the
   heatmap. Check its leniency column is in line with the others.

## Common pitfalls

- **Different tool signatures across subjects.** If one framework wraps
  tools and mutates their arg schema, the agent behaviour changes. Share
  tools at the Python function level, wrap at the adapter boundary only.
- **Different judge per subject.** Tempting if one framework emits prose
  and another emits JSON — resist. Fix the adapter to emit the canonical
  schema instead (see `structured-output-troubleshooting.md`).
- **Different model IDs leaking in.** LiteLLM / bedrock model prefixes
  differ across frameworks. Log the resolved `model_id` in each row and
  verify it matches your intent before trusting the leaderboard.
- **Parallelism.** Running all subjects in parallel speeds things up but
  can cause rate limit artifacts that look like quality differences. For
  trustworthy numbers, run sequentially the first time.
- **Cherry-picking cases where your preferred subject wins.** If you find
  yourself adding or removing test cases mid-benchmark, stop and freeze the
  seed set first.
